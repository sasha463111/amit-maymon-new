# System Audit — 2026-09-18

Deep audit of permissions, code correctness and database integrity, triggered by
"file uploads don't work for Ilana" and widening from there. **Twelve production
faults found**, eleven fixed and deployed, one deferred by decision.

---

## The single root cause behind most of it

`profiles.branch_id` (single UUID) was replaced by `profiles.branch_ids` (UUID
array) in an earlier schema change. The obvious call sites were updated; these
were not. Because a Supabase query for a non-existent column **fails rather than
returning null**, every one of these silently fell through to "deny" or "empty":

```ts
const { data: profile } = await supabase.from('profiles').select('branch_id, ...')
// profile === null  →  role === undefined  →  permission check denies everyone
```

**When a column is renamed, grep the entire repo AND every database function and
RLS policy.** Server Actions, RLS policies, SQL helper functions and storage
helpers all reference columns independently.

## Permissions: from decorative to authoritative

`role_permissions` was **display-only**. Settings rendered switches, the CEO
flipped them, rows saved — and nothing read them. It also displayed two false
claims (SERVICE_ADVISOR able to create cases and manage extras, which the code
always refused).

Now it governs all nine actions across three layers — UI, server action, RLS.
See **Standing Rule #5** in `CLAUDE.md` for the full contract and the checklist
for adding a new action.

`create_referral` was added as the ninth action. Previously opening a referral
was hard-coded to OFFICE/CEO with no setting able to change it — which is why
"נסיה and ערן cannot open referrals" had no fix short of a code change.

**Behaviour did not change on the day.** Six actions already matched the code
exactly; the two false SERVICE_ADVISOR rows were set to false to match what was
actually enforced; `create_referral` defaults to OFFICE + CEO. Everything is now
changeable from Settings and the change actually takes effect.

## Notifications: two separate channels

Do not conflate these — it caused real confusion during the audit.

| | In-app (bell) | Push (device) |
|---|---|---|
| Storage | `notifications` table | `push_subscriptions` table |
| Works for | everyone | only users who accepted the browser prompt |
| Ilana | 86 received | **0 devices registered** |

Ilana **does** get notifications. What she lacks is push — the alert that fires
while the app is closed. That requires a one-time browser opt-in on her own
device and **cannot be fixed server-side**.

## Still open

**Database backup** — deferred by decision, to be discussed with Amit.

The daily GitHub Actions backup has failed every day since 2026-09-04. Two
independent causes: the `SUPABASE_PASSWORD` secret **does not exist** in the
repository, and the host pointed at the API endpoint rather than the database
(and Supabase has since dropped IPv4 from direct database connections, so GitHub
runners time out regardless). The workflow is fixed — pooler host, fail-fast on
missing secret, fail on empty dump — but **cannot run until the secret is added**.

The project is on Supabase's **free** plan, which includes no managed backup.

| Option | Monthly | What you get |
|---|---|---|
| Current (free) | $0 | No managed backup at all |
| Fix the self-export | $0 | Add the secret; dumps kept 30 days as GitHub artifacts |
| Supabase Pro | $25 | Automatic daily backups, restore up to 7 days back from the dashboard |
| Pro + PITR | $125+ | Restore to a specific moment — likely overkill at this scale |

⚠️ Database backups **exclude uploaded files** (case photos and documents) on
every plan. The database stores only metadata about them. If those files matter
for recovery, they need a separate backup solution regardless of plan.

## Verification standard used

Every finding was confirmed against the live production schema before being
called a bug, and every fix re-queried after applying.

This mattered: earlier in the session an "I'm 100% certain" verification was run
against `ilana@tehila.test` — a **disabled test account** — while the real users
are `reception@` and `ilanit@`. Conclusions drawn from the wrong row are worse
than no conclusion, because they get reported as certainty.

**Confirm which row you are testing before trusting the result.**
